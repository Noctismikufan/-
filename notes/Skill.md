# Skill（技能）

> 一句话定义：Skill 是打包好的、可被 AI 按需加载的专业能力模块，它把特定任务的操作流程和知识固化下来，让 AI 在遇到对应场景时能按既定方法可靠执行。

## 一、它解决什么问题

通用大模型虽然什么都能聊，但在专业任务上常常"不专业"：不知道你们公司的规范、不懂某个工具的特定用法、每次都要重新摸索同样的步骤。

如果每次都靠用户现场把要求写进提示词，会有三个问题：

1. **重复劳动**：同一个任务的说明要反复写
2. **质量不稳**：每次描述不同，结果参差不齐
3. **无法积累**：经验无法沉淀下来复用

**Skill 就是为"把专业能力固化、复用、按需调用"而生。** 它相当于给 AI 配了一套"专业操作手册"，遇到对应场景就翻开照做。

## 二、核心定义

Skill = **元数据 + 操作指令 + 可选资源**。

拆解定义中的关键词：

- **元数据**：`name`（名称）和 `description`（描述），决定 AI **何时**该用它
- **操作指令**：SKILL.md 正文，告诉 AI **怎么**做这件事
- **可选资源**：
  - `scripts/`：可执行的确定性代码
  - `references/`：需要时加载的参考资料
  - `assets/`：输出时要用的模板、字体等文件
- **按需加载**：Skill 不会一开始就全部塞进上下文，而是**先看元数据判断是否相关，相关才加载正文**，正文里提到的资源再按需加载

## 三、工作原理 / 关键机制

Skill 采用**三级渐进式加载**（Progressive Disclosure），这是它最精妙的设计：

| 层级 | 内容 | 何时进入上下文 | 体量 |
|------|------|--------------|------|
| 第 1 级 | 名称 + 描述 | **始终**在上下文 | ~100 词 |
| 第 2 级 | SKILL.md 正文 | 判定相关时加载 | < 5k 词 |
| 第 3 级 | scripts/references/assets | 真正需要时才加载 | 不限 |

工作流程：

1. **扫描**：AI 启动时只加载所有 Skill 的名称和描述
2. **匹配**：用户提出任务时，AI 用描述判断哪个 Skill 相关
3. **加载**：相关的 Skill 才把正文读进上下文
4. **执行**：按正文的指令操作，需要时再读取 references 或运行 scripts
5. **输出**：按 Skill 规定的方式产出结果

**为什么这样设计？** 因为上下文窗口有限。如果有 50 个 Skill 每个都几千字，全部加载会直接撑爆上下文。分级加载让 Skill 的数量增长**不会线性推高上下文占用**，从而支持大量 Skill 并存。

## 四、一个恰当的类比

把 Skill 类比成**给新员工的"岗位操作手册"**：

- 手册封面写着"财务报销流程""服务器部署流程"——这是**元数据**，让人一眼知道该翻哪本
- 员工遇到对应任务时才**翻开**那本手册照做——这是**按需加载**
- 手册里可能还附了模板表格、脚本工具——这是 **assets 和 scripts**

**类比的局限**：手册是给人看的，人能理解模糊表述；而 SKILL.md 是给 AI 执行的，措辞必须精确、无歧义。另外，人可能同时翻多本手册，而 Skill 的加载受上下文容量约束，不是无限并行的。

## 五、具体示例

**示例：一个"概念学习资料生成"Skill**

- **元数据**：名称 `concept-learning-material`，描述"当用户要求学习、讲解某个概念时使用"
- **正文**：规定了固定的八节结构（定义→问题→原理→类比→示例→误区→相邻概念→延伸）、写作风格、质量自检清单
- **references/**：`quality-checklist.md`（质量检查清单）、`writing-guide.md`（写作指南）

**效果对比**：
- 没有 Skill：用户说"帮我学习 Agent"，AI 每次输出格式随意、深浅不一
- 有 Skill：AI 自动按统一结构输出，且用清单自检，质量稳定可复现

## 六、常见误区

❌ **误解一**：Skill 就是提示词模板
✅ **正解**：提示词模板只是一段文字，Skill 是**完整的目录结构**——含元数据、正文、可执行脚本、参考文件，还遵循按需加载机制。Skill 是可分发、可版本管理的"能力包"。

❌ **误解二**：装了 Skill 就会占用大量上下文
✅ **正解**：平时只有名称和描述（约 100 词）在上下文里，正文和资源都是**按需加载**的。这正是渐进式加载设计的目的。

❌ **误解三**：Skill 能自己执行代码
✅ **正解**：Skill 本身不执行任何东西。它只是**给 AI 的说明书**，告诉 AI 该运行哪个脚本、该读哪个文件。执行动作的是 AI（借助其工具）。

❌ **误解四**：Skill 和工具（Tool）是一回事
✅ **正解**：工具是 AI 能调用的**具体功能**（如搜索、执行代码）；Skill 是**组织知识和流程的说明文档**，它可能指导 AI 去用某些工具，但两者层级不同。

## 七、与相邻概念的关系

| 概念 | 与 Skill 的区别 |
|------|----------------|
| **提示词（Prompt）** | 提示词是一次性的输入；Skill 是可复用、可版本化的能力包 |
| **工具（Tool）** | 工具是可调用的功能接口；Skill 是教 AI"何时、如何"使用能力的说明书 |
| **MCP** | MCP 是连接外部服务的**协议**；Skill 是固化**流程知识**的文档包，两者可配合使用 |
| **Agent** | Agent 是执行主体；Skill 是 Agent 可以加载的**专业能力**，一个 Agent 可拥有多个 Skill |
| **上下文** | Skill 的渐进式加载正是为了**节省上下文**而设计 |

## 八、延伸学习

1. **渐进式加载（Progressive Disclosure）**——Skill 设计的核心思想，也适用于其他上下文管理场景
2. **MCP（Model Context Protocol）**——与 Skill 互补的外部能力接入协议
3. **Agent 与 Skill 的配合**——Agent 如何调度多个 Skill 完成复杂任务
4. **Skill 的工程化**——版本管理、测试、分发（如打包为 zip 分发）
